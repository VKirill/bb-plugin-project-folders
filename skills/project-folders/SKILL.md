# Projects and folders
Resolve project and section IDs with `bb project-folders list --json`. Each section has an explicit host and path.
Create a real section: `bb project-folders create <project-id> <parent-id-or-dash> <name> <relative-path> [host-id] --json`. Quote names and paths. `-` selects the project root; a host selects that project's registered source on that host. A nested section (under a section or a group) may use another host where the project has a source; it then starts in that host's project folder. `<relative-path>` may also be an absolute folder on the host outside the project (for example a website on a server), the project folder itself, or a folder already used by another section; several sections may share one path. It must not overlap another BB project. Archiving a shared or external section keeps its files in place. A section can have its own folder on each device (`bb project-folders path-set <folder-id> <host-id> <path>`), like a project copy. Missing sources and offline devices must never cause fallback to a different device. Existing directories may be registered without overwriting contents.
A project may hold one working copy per device: `bb project-folders copy-add <project-id> <host-id> <path>` registers and seeds an additional source; `copy-remove <project-id> <host-id>` removes it. The last copy is protected, and a copy with sections or chats in the tree is refused. The tree lists one root per source (`root:<host-id>`); never treat another device's copy as a fallback workspace.
New projects are created using the core BB project API, through the plugin's New project dialog or the documented core CLI. The dialog includes device, name and folder selection. Do not change a project's existing roots just to organize sections.
Plugin settings → **Projects → New project starting folder** sets the dialog's initial parent directory and folder-browser location. Use an absolute path on the selected device; blank uses that device's home directory. The shared preference is `prefs.projects.startingFolder` in `prefs_get` / `prefs_save`, not `bb plugin config`. An unavailable directory shows a warning and falls back to the same device's home directory. Explicit folder choices override the suggestion; preference changes take effect on the next dialog opening or device change. The management page and BB plugin settings expose the same field.
New chats use BB's composer and preserve model, attachments and execution choices; the section's workspace path is explicit. The composer folder picker lists each project once; the composer's machine control selects which device copy a root chat opens in. A section can have a folder on each device; chats follow the composer machine when that path exists. Keep generated documents, notes and temporary files in `<workspace>/.bb/chats/<thread-id>/{artifacts,notes,tmp}/`. Code and requested working deliverables follow the user's structure. Read applicable ancestor AGENTS.md files. UI rule edits use SHA comparison and preserve concurrent edits. Renaming a section changes its display name only; changing the directory is the section's own move action.
Asked to write rules for a project or a section — "правила agents.md для раздела", "set up the rules here" — do not edit `AGENTS.md` by hand: the plugin keeps its own record, an edit behind its back leaves the card on **Default**, and the next apply overwrites the text. Use `bb project-folders rules show|set` and read [references/rules.md](references/rules.md) for the modes, the inheritance, the flags and what section rules should contain. The short form: `bb project-folders rules set <project-id> <folder-id-or-dash> --mode custom --template "<markdown>" --json`, then read the result back.

New sections can be seeded with default rules: plugin settings hold shared project and sections templates, written between `<!-- bb-project-folders:agents:start -->` and `:end` markers at the end of a created AGENTS.md. Rules are hierarchical: a project may override both templates for its own subtree (project_rules), a section of any depth may set its own template (folder_rules), and the nearest override wins — otherwise the project's, otherwise the shared one. Groups have no rules: no seeding and no Rules action. Saving `mode=custom` stamps that place's own template into its `AGENTS.md` managed block at once — a project into every device copy, a section into its own folder. A folder may also be kept on its own file (`mode=manual`, the default for an AGENTS.md without the plugin markers): the plugin writes nothing there and `agents_apply` skips it. Content above the markers belongs to the user and must never be rewritten; the managed block is updated in place when the template changes. Project and section order is manual: `reorder` stores the order; never sort by name silently.
BB retains canonical chat storage. The plugin exports the timeline to `.bb/chats/<thread-id>/history/` in a persistent background queue after creation, idle and archive. Automatic exports are coalesced, run one at a time and may lag behind BB; unchanged snapshots are skipped. `history/index.json` selects the snapshot directory and page count, newest first. Attachment binaries remain in BB's storage. `bb project-folders sync <thread-id>` retries an export.
## Archive and restore
`bb project-folders archive <folder-id>` moves the complete directory tree to `<project-source>/.bb/archive/sections/<archive-id>/folder`, writes a manifest, archives its chats and preserves rules, files, history and nested section IDs. `forget` is a compatibility alias for archive, no longer a detach-only operation.
The section menu is **Delete**. It offers three modes via `bb project-folders remove-section <folder-id> archive|unbind|purge` (RPC `section_remove`): `archive` is the same move; `unbind` leaves files on disk, drops the section from the tree and archives chats opened there (BB chat archive, not the section archive); `purge` deletes those chats and, when the folder is inside the project and not shared, deletes the directory. Refuse `purge` when another BB project lives in the folder, another section shares the path, or the folder is outside the project — use `unbind`. Do not archive a section when the user only wants it off the tree.
Active work and queued messages must finish before a move. A section containing another BB project's source cannot be moved implicitly. The plugin rejects message dispatch in archived chats until restored.
`bb project-folders archives --json` lists archives and interrupted operations. Retry `archive <folder-id>` for an interrupted archive; `restore <archive-id>` restores an archived section or retries an interrupted restore. State persists across reloads. Do not manipulate the journal manually.
`bb project-folders restore <archive-id>` restores the original path and previously unarchived chats; it never overwrites an occupied original path. Restore the parent first when necessary.
Creating a section with an archived name in the same project/device requires a restore-or-create-new choice in the UI. Do not silently create a fresh directory instead of offering restoration. Permanently deleting archives is not implemented.

## Delete a project
`bb project-folders delete-project <project-id> keep|archive` removes the BB project from the tree. `keep` leaves folders on disk. `archive` moves each local source to `<parent>/.bb/archive/projects/<id>/folder` on that host. BB chats of that project are deleted. Refuse `archive` when there is no local folder, or when a folder is another project's section or contains another project source. Do not delete a project on the user's behalf when they only asked for the menu; they use the **Delete** action themselves.

## Move a project
Use the project card or three-dot Move action to select a new path on the same host and disk volume. This moves the complete source directory, including dotfiles, exports and archives, and updates project and plugin metadata. BB's central database and attachments remain in BB; outside files and other-device sources are unchanged. The original path becomes a compatibility symlink for existing BB environments: do not remove it while those chats rely on it. Finish running chats and queued work first. Home/runtime directories and linked Git worktrees are rejected. Pending moves block messages and can be retried from the management page. Never substitute a source-path update alone for a physical project move.

Filing a chat: the `thread_place` RPC `{ threadId, projectId, folderId }` (`folderId: null` = project root) records where a chat is listed, `thread_place_clear` returns it to the folder it works in. Only the place in the tree changes, so any section of the chat's project is a valid destination, including one on another device; a group is refused. The UI exposes this as Move to section in the shared chat right-click/ellipsis menu and drag/drop, and marks a chat filed away from its working folder. Project and section headings use the same right-click menu as their ellipsis button. Moving the working folder itself is the `thread_move` RPC, which the UI uses whenever the destination is on the chat's own device. It first tries the core directory-update API (`threads.update({ experimental_directory })`); when BB rejects the field (get-bb/bb#3904) it asks the chat instead — one agent-only message carrying `[project-folders:relocate]` tells the chat to call its own `update_environment_directory`. The chat is filed into the destination at once (`thread_places`), so the tree never waits on an agent. The job stays on the `thread_moves` barrier, which does not block the chat while it is only "asked"; the first idle after the asked turn settles it — `moved` when the environment is the destination (storage follows, filing dropped), `kept` when it is not (folder unchanged, filing stays, job cleared), which is what a provider without the tool gets. A chat still cannot change machine, so a destination on another device files the chat only.

CLI: `bb project-folders place-chat <thread-id> <project-id> <folder-id-or-dash>` files a chat, `unplace-chat <thread-id>` undoes it; `move-chat <thread-id> <project-id> <folder-id-or-dash> <host-id>` moves the working folder and needs the core API. A dash selects the project root.

## Move a section
Sections have **Change path** in their ⋯ / right-click menu and on the section card; CLI: `bb project-folders move-section <folder-id> <absolute-path>`. The section stays inside its project folder on the same device and must not land inside another section or on a registered path. If the destination does not exist, the whole section folder relocates, including hidden files and chat history; if the destination exists while the recorded path does not, the section re-links to it — this repairs a folder renamed outside BB. Either way the old path becomes a compatibility symlink for existing chat environments: do not remove it while those chats rely on it. Nested sections, chat exports and archive manifests follow the move; running chats and queued work must finish first, and an interrupted move persists a barrier that is retried from the same destination (the **Unfinished section moves** card or the same CLI call). Workspace paths recorded before a completed move resolve through it, so bindings, chat labels and exports keep working.

Folder picker: project and section creation dialogs can create child folders on the selected host. Deletion is confirmed and uses nonrecursive rmdir; nonempty, symlink, and registered project/section directories are rejected. Use archive/restore for sections with history.

## Execution defaults: provider, model, agent
What a new chat starts with can be pinned per place: RPC `execution_read` / `execution_save` / `execution_agents`, scope `{kind:"global"}` | `{kind:"project",projectId}` | `{kind:"folder",projectId,folderId}`, table `execution_defaults` (keys `g`, `p:<projectId>`, `f:<folderId>`). Three independent groups: the model pin (providerId + model, with reasoningLevel and serviceTier), the permissionMode, and the agent (`agentMode:"agent"` + agentId, or `agentMode:"none"` for an explicit no-agent). Resolution is nearest-first — the section, its ancestors, the project, the plugin-wide default — one group at a time; an unpinned group falls through to BB's own remembered project defaults. Sections of any depth may pin, like AGENTS.md rules.
The plugin never overrides the composer: the resolved values are passed to `experimental_NewThreadComposer` as `default*` seeds, so the user's own pickers still decide that chat. Do not "enforce" them in `spawn`.
Agents belong to the optional CLI Agents plugin (`bb.sdk.plugins.callRpc`, pluginId `cli-agents`, methods `catalog`, `pending`, `select`, `clearPending`); only claude-code, codex and acp-opencode have them. `spawn` binds a pinned agent by appending CLI Agents' `[cli-agents-selection:<token>]` marker as an agent-only part of the first message, which ties it to that one chat, then clears the project-wide pending choice. A pending choice made by the user in the composer wins and the plugin stays out. A pinned agent that cannot be applied fails the spawn with a message naming the place; a composer switched to a CLI without agents is not a failure.

## Preferences and appearance
Chat list settings, levels' appearance and per-item looks live on the BB server (`prefs_get`, `prefs_save`, `item_style_save`; tables `preferences` and `item_styles`, keys `p:<projectId>` / `f:<folderId>`). Icons are `icon:<Name>` from the plugin's curated set or `emoji:<char>`; colors are palette tokens or `#rrggbb`. Shared AGENTS.md rules are stored in the `preferences` row `agents` (RPC `agents_config` / `agents_config_save`), not in declarative plugin settings, so `bb plugin config` does not show them. The management page (tree sidebar `SettingsNav` + `SettingsPane`, deep link `settings/<section>`) and the BB settings page (`PluginSettings` rail) render the same sections; don't add a setting to only one of them.
